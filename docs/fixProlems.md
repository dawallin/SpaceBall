# FixProblems: Space Ball 3D engine findings (triage for next agent)

Focused review of the current Babylon.js/Havok implementation against the specs and UI shows three blocking categories: entry-shell mismatches, physics/telemetry gaps, and scoring layout deviations. Each item below references the exact files/lines to align with the written requirements before further implementation.

## Entry points and boot flow
- **Dev entry skips engine scripts.** The published root `index.html` loads Babylon/Havok and only then injects `src/main.js`, while `src/index.html` ships the full UI without either engine script. Opening `src/index.html` (common during local iteration) guarantees `window.BABYLON` is undefined before bootstrap, tripping the red crash banner in `main.js` and halting the scene. Consolidate to one HTML shell (or add matching script tags to `src/index.html`) so both dev and production paths stage the engine before the module runs. 【F:index.html†L73-L96】【F:src/index.html†L1-L72】【F:src/main.js†L34-L111】
- **No fallback when CDNs fail.** Both shells poll indefinitely for CDN-loaded globals; if either script 404s, the status bar loops and the game never mounts. Introduce a bounded retry with an error surface (and preferably ship local copies) so bootstrap fails deterministically instead of spinning. 【F:index.html†L73-L96】【F:src/main.js†L12-L111】

## Physics and telemetry gaps
- **Gravity constants diverge from the geometry model.** Gameplay maths in `tiltToAcceleration` default to a 40 m/s² base while the geometry model and physics engine both assume Earth gravity (9.81 m/s²). This makes any rail-angle tuning incompatible with the spec’d “realistic rod-ball physics.” Drive both from one shared constant before retuning tilt, acceleration, and descent rates. 【F:src/control-logic.js†L10-L28】【F:src/geometry.js†L92-L145】【F:docs/specs/spaceball_physics.feature†L1-L61】
- **Rails don’t push kinematic bodies during tilt/angle changes.** Visual rails update every frame via `updateRailMeshes`, but the physics aggregates only receive transforms through `syncRailBodies` based on the current collider nodes. Because `updateBoardTilt` rotates only the `boardPivot` (visual parent), the colliders’ world transforms never change when tilt sliders move, leaving Havok bodies effectively flat while the mesh tilts. Recompute collider transforms from the tilted geometry and send `setTargetTransform`/`setTransformation` on every tilt/angle update before the physics step. 【F:src/main.js†L780-L880】【F:src/main.js†L1158-L1235】
- **Displacement tracking ignores uphill motion.** `updateBallTelemetry` only adds distance when the ball moves downward (negative Y), so reversing back to the apex after closing the rails does not reduce or zero the travelled metres. The core gameplay spec expects the ball to climb back and settle, with score tied to total travel before a drop. Track signed displacement (or total path length) so the score readout and drop conditions reflect the actual movement, then assert this behaviour with automated checks. 【F:src/main.js†L1238-L1287】【F:docs/specs/core_gameplay.feature†L9-L37】

## Scoring layout mismatches
- **Pockets are laid out horizontally instead of stacked under the chute.** `createScoringTargets` spreads targets across the board’s X axis, while the design reference calls for vertically stacked pockets centered beneath the rail exit (Pluto at the lowest, widest slot). Adjust target coordinates to follow the centerline beneath the rails and match the ordering/spacing shown in the sketch before binding any scoring logic. 【F:src/geometry.js†L52-L93】【F:docs/design_reference.md†L4-L16】

## Immediate actions for the next pass
1. Remove the duplicated shell or align `src/index.html` with the root `index.html`, adding deterministic failure handling for missing Babylon/Havok bundles.
2. Normalize gravity/acceleration to the geometry constant and propagate tilt/angle updates to the Havok bodies every frame so physics matches the rendered rails.
3. Rework displacement/score tracking and scoring target layout to satisfy the core gameplay and design specs, and back the fixes with automated scenarios that mirror `core_gameplay.feature` and `spaceball_physics.feature`.
